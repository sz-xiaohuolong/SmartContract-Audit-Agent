# 第一批真实案例来源选择提案

更新：2026-09-25。状态：**用户已批准来源与访问控制／重入范围；尚未准入任何真实样本**。本文件只确定核验顺序和用途，不改变数据划分或知识库激活状态。第一批核验严格限制在 10～15 个高质量样本，不做全量人工排查；当前十项待审名单见[首次核验记录](FIRST_BATCH_AUDIT.md)。

## 结论

第一批先做访问控制与重入两个方向的小规模、逐事件核验。访问控制以 **ASE 2025 基准**为主要待审事件索引；重入以 **SCRUBD V6.0** 为待审事件索引；**SmartBugs Curated** 只作为待审知识案例候选。真实漏洞—修复对优先沿原始审计报告与项目维护者的修复提交追溯；**Proof-of-Patch** 的 `003`（访问控制候选）和 `077`（重入候选）可作首批追溯线索，但其数据仓库未声明许可，不能直接入库。ACFix 暂作相关研究和案例线索，不把模型生成的修复自动标为安全。当前可以进入正式知识快照的真实案例数仍为 **0**。

首次先导以能核实的独立项目数决定规模，不为凑样本数量放宽证据要求。目标是先查明每类是否有数个可用的独立项目及真实修复对，再冻结知识／开发／验证／锁定测试的项目组划分。

## 首批人工核验与准入规则

1. 每个事件保存原始报告 URL、漏洞位置、项目及版本／提交、原始源码哈希、许可证据；如有修复，再记录维护者补丁提交及其覆盖的漏洞路径。报告、源码、补丁有任一项无法对应，标为待审，不生成安全标签。
2. 优先从 ASE 的 Code4rena 与有源码的 CVE／事件中找访问控制案例；从 SCRUBD 的真实案例中找重入案例；用 Proof-of-Patch `003`、`077` 验证真实补丁对追溯过程。两类案例均须检查跨仓库重复。
3. 同项目、同漏洞事件、同补丁对、完全重复或近克隆源码，以及从它们写出的摘要、报告和知识文档统一组 ID。整组只进入 knowledge、development、validation、locked-test 之一。锁定测试在方法冻结前不打开。
4. 知识快照只接受许可与逐案例证据均通过的 knowledge 组；构建后逐项核对数量、哈希和 Milvus 集合读回完整性，验证通过才切换激活指针。开发／验证／锁定测试组不得成为知识文档。
5. D1 在相同知识快照、候选池和完整提示 token 上限下，与 Dense、Hybrid、普通正反例及简单条件过滤比较；由独立审核者标目标—案例适用性、支持／反证价值或 UNKNOWN。真实补丁对、人工改造和合成样本分别报告。

## 当前阻塞与用户审核点

- **许可**：SCRUBD、Proof-of-Patch、ACFix 的数据仓库未声明许可证；ASE／SmartBugs 的仓库许可证也不能代替各原项目源码与报告的使用许可核验。
- **标签**：ASE 和 SmartBugs 主要提供漏洞案例；现有来源尚未给出可直接采信的成组安全负例。SCRUBD 的“非漏洞”与 ACFix 的修复输出均需单独证明。
- **版本**：SCRUBD 标签曾多次修正；只按固定的 V6.0 提交审查，不能混合旧版结果。ASE 字节码独有的 18 个事件不适合当前源码检索接口。
- **决策**：请审核上述来源优先级和首批只做访问控制／重入的范围。审核通过后，下一步才逐事件建来源台账、核对原始证据与许可、形成隔离组并报告实际准入数。未通过 G1 前不建立或激活正式知识快照，也不宣称 D1 真实效果。
