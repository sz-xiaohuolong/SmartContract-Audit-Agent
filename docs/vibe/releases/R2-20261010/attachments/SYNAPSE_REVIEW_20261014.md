## 2. 论文实际做了什么

### 2.1 方法主线

论文针对复杂业务逻辑审计中的三个困难：长上下文注意力不足、缺少面向安全分析的代码工具、通用模型缺少漏洞领域经验。其工作流是代码预处理、思维模板检索与实例化、双 Researcher 协作、Verifier 复核（§4，图2）。

1. **预处理与代码记忆**：用 ANTLR 进行无需完整编译的语法解析，再处理 Import／Using 等信息；按函数和文档块建立代码语义检索。标准实现排除同时比较签名与 AST 结构，不能简化成按文件名或函数名排除（§4.1）。
2. **焦点上下文**：按需组合目标函数 `ff`、修饰器 `fm`、传递可达内部函数 `fi`、合约状态变量 `fv`。原文 `fv` 指该合约的全部私有与公开状态变量；进一步筛成相关变量是我们的拟议优化。`fi` 的完整性依赖其生成的调用图（§4.2.2，图4）。
3. **BoVRT**：从超过14,000份报告中蒸馏1,247个模板，区分针对特定模式的 targeted thoughts 和推导项目不变量的 invariant thoughts。五元组第一项是**合约类型**，其余为直接问题、推理步骤、状态变量和函数签名；并非单纯的漏洞类别标签（§4.3.1，表1、表2）。
4. **实例化**：先映射具体函数，再映射状态变量，最后结合业务流程调整检查步骤。检索按合约类型过滤，top-k 为10。代码库 RAG 与 BoVRT 是两条用途不同的检索路径；论文没有否定所有 RAG（§4.1.4、§4.3.1，算法1）。
5. **协作与复核**：代码模型和推理模型各自产生发现，再互评并进行一轮后续分析。Verifier 对事实准确性、逻辑关联、相关性、额外假设等六项标准逐一回答 Yes／No，仅全部 Yes 时纳入报告（§4.3.2～4.3.3）。这些是模型复核标准，不等价于形式证明或 EVM 可利用性证明。

“可执行推理路径”在本文语境中指可以被代理遵循的分析步骤。SYNAPSE 没有在这些步骤上提供与本工程编译收据相同的确定性证明契约，不能仅凭这个词推断其具备可执行 PoC。

### 2.3 最值得压力测试的假设

**最脆弱的假设：被筛选、检索和聚焦的上下文已经足以判断所提业务属性。** 如果权限保护藏在未解析调用、代理实现或被排除的库中，模型可以形成连贯解释，却缺少决定性事实。表9的15个上下文排除漏报和§5.4的内部函数权限检查误报，直接说明这个假设会失败。图3的提示还要求跳过无法解析的外部调用；迁移到本工程时，这些调用必须登记为闭包缺口。

针对这个假设的最强对照，是保持外层函数近似不变，仅改变被调用保护函数、库实现或可变权限状态。系统应随证据改变结论；缺失实现时应弃权。另一个对照是加入语义保持的标识符重命名和无关长代码，分别观察发现率、绑定率和弃权率，而非只查看模型理由是否流畅。

论文的创新在于模板实例化、上下文工具和协作工作流的组合。六道自然语言核查能减少幻觉，但不能独立保证上下文完备、属性正确或交易可行。我们可进一步研究这些分析步骤如何消费可回查的程序证据；这种研究方向仍需与既有LLM＋程序验证工作比较后才能提出新颖性主张。

## 5. 可迁移的设计与研究问题

### 5.1 D1：从变化窗口到可审核的检查规约

先从现有知识划分和已审核配对整理少量AC／RE模板。每条包含检查问题、适用前提、目标角色、所需程序证据、检查步骤、补丁指针、适用性和缺口；保留原pair／chunk／来源摘要。实例化应输出“用哪个入口、哪个声明、哪个索引和字段、哪个状态版本检查哪个命题”，不能只替换变量名。

例如CEI模板应询问：实际CALL前的余额写入是否作用于同一主体、同一资源和当前状态版本；其他可达入口是否仍可消费旧状态；统一锁是否覆盖这些入口。对CALL前仅写了另一key、写了memory副本或调用后必回滚的例子，模板必须要求进一步核对。这个示例是我们的拟议规约，不是已验模板，也不含目标标签。

**研究问题RQ-A**：在相同来源候选池、预算、模型和输入下，模板表述与证据实例化分别能否提高位置与理由均正确的发现率？如果只有模板语气变化有效，应据实报告，不能归因于正式条件绑定。

### 5.2 上下文：关注局部，同时保留全局义务

先增加确定性的焦点上下文展示与消费回执，保留绝对行号和原始字节跨度。编译可用时从已验AST／调用图建立闭包；只解析语法时明确未解析的重载、继承、导入和动态调用。跨入口写入者、权限变更者和回调边界也必须能查询，不能把`ff+fm+fi+fv`误称为完整D2保护闭包。

当前FULL输入契约要求消费完整清理源码。第一步保留FULL正文，焦点目录只提供索引与回查展示；后续若要以切片替换全文，需要新增显式输入模式、更新有效规格并独立建实验，不续写旧计划。原研究协议也要求FULL输入，不能静默改写。

**研究问题RQ-B**：固定总预算时，闭包可见的上下文组织能否改善长源码定位，同时在缺依赖时保持明确弃权？不能仅用平均token减少来证明正确性。

### 5.3 复核：把独立性放在证据路径上

采用独立于模型理由的确定性复核：引用是否存在、源码与收据是否一致、候选是否唯一绑定、主体／资源是否同一、必要上下文是否齐全、路径是否正常提交。复核输出通过、冲突和未决原因，而最终漏洞三态仍由现行D2门槛决定。

如要增加双Researcher实验，应保留各自初始候选、互评内容、最终候选及全部usage，记录单模型／自复核／双模型的分别成本和误杀率。模型同意不能作为D2佐证；当前计划默认新增付费请求为0。

**研究问题RQ-C**：在固定候选上，证据复核能否减少错误接受，且不会依靠扩大弃权来制造精确率提升？沿用四臂比较，结合独立候选标签报告覆盖率、错误率和UNKNOWN原因。

### 5.4 不变量研究：先确认规约，再验证路径

Munchables启发我们研究同实体的业务状态关系。拟议属性可表述为：对已经确认处于占用状态的实体，若业务规定实体位置与占用记录互为对应，正常迁移完成后双方仍应一致。这个属性必须登记生命周期、对象身份、例外和来源；不能直接用“两个字段都出现赋值”替代。

当前R2仅冻结AC／RE。业务状态一致性作为后续范围提案，需另行确认数据、属性语义、工具佐证策略与验收；不能复用AC／RE的检测器映射或把 `state_version` 改名后宣称已覆盖MUB。最小研究可在一个可核源码／真实修复对及正负变体上检验属性和反例，正向执行仍是正常业务路径。

可用于论文的审慎表述是：**借鉴SYNAPSE的漏洞思维实例化与焦点上下文，本工程研究将检查步骤绑定到程序事实和保护义务，在有限语义范围内给出可回查的支持、反驳或未知结果。** 这说明技术路线；效果、可利用性和创新性仍分别依赖实验与相关工作审查。

## 6. 一周内的最小验证建议

优先完成两个零模型验证：第一，复用发现阶段真实编译收据，重放最新163与历史133／151全部候选，检验ID接缝是否消失且漂移／多义仍拒绝；第二，围绕AC／RE真实维护者修复和内部保护上下文制作独立审核的正负挑战，验证D2正反边界。两者直接决定后续提示实验是否有可靠测量基础。

随后仅准备知识划分内8～12条可溯源检查模板、完整消费回执及待审消融协议。没有真实模型调用就不能回答模板是否提高发现率。新模型实验需独立来源／候选审核、预算与输入契约准入后，再按具体授权执行；一周是规划窗口，不是完成承诺。详细任务、依赖和验收由[统一实施计划](../IMPLEMENTATION_PLAN.md#synapse-优化任务)维护。
