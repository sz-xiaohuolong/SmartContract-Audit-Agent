# 概念速查与 SimpleDAO 审计故事

读完本页，可以看懂检索案例、漏洞候选和六项检查之间的关系。这里的 SimpleDAO 是公开基准中的真实源码；讲解涉及的本机演练使用已登记候选，模型发现过程另行说明。

## D1：把漏洞和修复放在一起比较

普通检索像按题目关键词找参考资料。D1 希望进一步找到同一类问题的漏洞代码与修复代码，让模型比较：修复增加了谁的权限检查，检查的是哪笔资产，检查和状态更新发生在危险操作之前还是之后。

D1 的研究名称是 Defect-Repair Contrastive Retrieval，本文称“安全条件差异检索”。可以把它理解为带修改说明的解题对照。对照帮助模型提出更具体的猜想，修复片段本身仍需要核实来源和适用条件。当前知识快照含 300 组、600 条自动标注知识，自动配对尚未得到独立的语义审核，不能把每组都称为已经验证正确的维护者补丁。

模型始终分析待审合约。相似案例中的权限名、余额键或锁可能对应另一种业务，因此系统还要检查案例条件能否对应到当前代码。当前默认 D1 仍使用原入选配对；新增的 10 条检查模板用于展示与保守绑定，其语义独立审核为 0，尚未测得模板提示带来的模型增益。

## D2：让六位审查官核对同一条猜想

D2 的研究名称是 Multi-Obligation Verification，本文称“路径覆盖多义务验证”。它把“这里可能有漏洞”拆成六个问题，结合编译器语法树、Slither 程序分析和有限的本机执行证据来回答。

| 检查 | 白话问题 | 重入提款时的直觉 |
|---|---|---|
| 主体权限 `actor` | 保护检查针对的到底是谁？ | 检查的账户是否就是发起提款的人？ |
| 资源绑定 `resource` | 检查和操作是否针对同一份资产或状态？ | 检查、付款和扣减是否使用同一账户的余额？ |
| 前置检查 `pre_risk_guard` | 保护是否在危险操作发生前生效？ | 付款前是否实际检查了余额条件？ |
| 入口覆盖 `entry_coverage` | 其他可调用入口是否也受到保护？ | 是否能从另一个提款或回调入口进入同一状态？ |
| 状态版本 `state_version` | 使用的是这次操作应当看到的状态吗？ | 回调时读到的是付款前的旧余额，还是已经扣减的余额？ |
| 绕过条件 `bypass` | 是否存在避开保护的执行路径？ | 能否在保护更新前重新进入？ |

六项检查评价的是保护条件。最终报告评价的是漏洞猜想，两者的状态对象不同：

| 状态 | 出现在漏洞候选上 | 出现在保护检查上 |
|---|---|---|
| 支持 `SUPPORTED` | 当前支持范围内，有程序反例及匹配的工具佐证 | 这项保护有证据成立 |
| 反驳 `REFUTED` | 完整保护证据能够排除这条特定猜想 | 这项保护被反例推翻 |
| 未知 `UNKNOWN` | 现有证据不足以支持或反驳 | 这项保护还无法判断 |

例如，SimpleDAO 的部分保护卡片显示红色，表示保护被推翻，最终漏洞候选却可以是“支持”。候选被反驳也只排除了该候选，报告没有据此检查完合约的所有安全问题。

## 三策略和四臂分别比较什么

三策略比较“模型在什么资料帮助下提出猜想”。

| 策略 | 模型看到的资料 | 对照意义 |
|---|---|---|
| Vanilla | 待审源码，不提供检索案例 | 零检索对照组 |
| Dense | 源码加语义向量相似的案例 | 传统语义检索对照组 |
| D1 | 源码加关注保护条件变化的配对案例 | 本项目提出的条件感知检索组 |

四臂比较“同一批猜想经过多强的检查”。它们复用保存候选，通常不需要再问模型。

| 检查臂 | 实际规则 | 主要盲点 |
|---|---|---|
| 无验证 `RAW_ACCEPTANCE` | 接受所有保存候选 | 无法过滤无依据猜想 |
| 仅看保护名称 `GUARD_NAME_EXISTS` | 唯一匹配函数含 `only*` 或 `nonReentrant` 修饰器名就拒绝候选 | 好听的名称可能没有实际保护 |
| 仅看检查行号 `LINE_CHECK` | 函数里存在不晚于候选行的 `require` 或 `assert` 就拒绝 | 检查可能针对别人、另一份资源，或只在某个分支生效 |
| 完整 D2 `FULL_D2` | 按程序证据输出支持、反驳或未知 | 当前引擎还有未覆盖的程序语义 |

弱规则的“接受／拒绝”只是过滤决策。它们没有产生 D2 所要求的程序证明。

## SimpleDAO：一份合约从输入到报告

### 1. 找到提款过程中的危险顺序

公开源码在 [simple_dao.sol](../../../../../smartbugs-curated/dataset/reentrancy/simple_dao.sol)。`withdraw` 先检查余额，再向调用者付款，最后扣减账户余额。源码第 19 行的低级调用可以把控制权交给收款方；此时余额扣减尚未发生。

这就像柜员先把钱递出去，稍后才更新账本。收款方回到同一提款流程时，账本可能仍显示旧余额。这个类比说明检查顺序的风险；最终判断还需要确认账户、资源、入口和执行证据。

### 2. 在工作台中选择或粘贴源码

选择“重入 · SimpleDAO · 公开学术基准”，可以直接进行本机离线演练。也可以粘贴 Solidity 源码并选择审计范围。系统保留原始行号，清理可能透露答案的注释，让模型分析代码而非注释中的漏洞标签。

### 3. 提取事实，再准备检索资料

Python 找到合约、函数、外部调用和余额写入。配置固定编译器后，系统从真实编译器输出读取 AST（抽象语法树，即代码的结构化表示），绑定准确的代码位置。编译收据保存源码、依赖、设置和编译产物，便于后续确认每一步分析的是同一份程序。

检索层根据选择的策略组织上下文。D1 关注的对照问题是：相似案例有没有把余额扣减移到付款之前，或用互斥锁覆盖相关入口？焦点索引可以定位函数、修饰器、内部调用和状态变量；当前模型输入仍是清理后的全文。

### 4. 取得一条具体猜想

真实模型模式由 Java 的 `HypothesisService` 请求模型。候选需要指出合约、完整函数签名、操作、位置和理由；系统检查这些引用是否对应源码。可理解为“`withdraw(uint256)` 的这次付款是否暴露了同账户余额的重入窗口”。这句话是讲解性转述，并非新增的真实模型响应。

离线演练直接使用已登记的 CALL 候选，跳过模型调用。因此，离线演练成功说明候选核验流程可运行，不能用于测量模型发现率。

### 5. 按六个问题核验

Slither 提供对应风险的静态告警；D2 检查实际路径、余额关系和状态顺序。静态事实足够时使用现有证明器；仍缺有限执行证据且满足提供器条件时，可显式使用本机 Anvil（本地以太坊执行环境），回放正常业务序列。

历史 SimpleDAO 本机演练的保护检查为：主体、资源、前置余额检查成立；入口、状态版本和旁路保护被反例推翻。最终登记漏洞候选得到 `SUPPORTED`。具体输出依据 [2026-10-13 工程报告](../experiments/2026-10-13_STAGE1_5_OFFLINE_REPORT.md) 和 [2026-10-14 实施报告](../experiments/2026-10-14_SYNAPSE_IMPLEMENTATION_REPORT.md)。这条结果说明了有限的执行顺序风险，尚未证明攻击可利用性。

### 6. 阅读和导出报告

先看当前候选结论，再看六项检查和源码位置。工具缺失、调用实现不明或相关入口未覆盖时，报告会解释为什么仍是未知。JSON 导出保留完整候选和依据；PDF 按钮使用浏览器打印。历史结果可以只读打开。

## 其他常见术语

| 术语 | 含义 |
|---|---|
| RAG | 先找相关资料，再让模型结合资料回答 |
| CEI | 先检查、再更新状态、最后与外部交互的代码顺序 |
| SlithIR | Slither 生成的中间表示，用于追踪变量、调用和状态写入 |
| 编译／工具双收据 | 分别保存编译器和 Slither 分析的输入与结果，再确认两者对应同一程序 |
| 保护闭包 | 与这条风险有关的入口、资源写入和调用都已纳入检查，没有遗漏的旁路 |
| EVM 有限见证 | 在具体初始状态和业务调用下观察到的执行证据；适用范围仅限该属性与执行 |
| 派生重放 | 用新引擎重新检查历史猜想，保留原模型响应和原实验结果 |
| 独立真值 | 由独立审核者确认的正确标签，用来判断候选是否真的对或错 |
| token | 模型计量文本的单位，不能直接用字节数代替 |
| 部分完成 `PARTIAL` | 一些工程或验收项已通过，其余仍未完成 |
| 尚未验证 `UNVERIFIED` | 缺少足够证据支持该研究结论 |
| Release / Slice | Release 是一轮版本目标；Slice 是其中可以单独实施和检查的小任务 |
