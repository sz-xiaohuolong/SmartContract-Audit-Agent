# SYNAPSE升级后的真实模型批量实验

为了检查这次工程修复在真实模型调用中是否有效，我们让53个合约分别使用三种策略：只读待审源码（VANILLA）、参考相似代码（DENSE）、参考漏洞与修复配对（D1）。三种策略共159个正式单元，使用相同模型和知识快照。

本次固定53目标×VANILLA／DENSE／D1，正式单元159，模型有效158、失败1、待执行0。正式请求尝试159次，含两个既定冒烟共161次，零自动重试。有效模型候选163条，D2为83支持／0反驳／80未知（49.08%）。

52个共同有效目标上，D1的F1为0.9787，略低于只读源码的VANILLA（0.9792）。D1精确率为1.0000，仍漏报两个wallet样本。这次观察没有证明模型发现增益；本批跨三个构建产物阶段，相关限制保留在下文。

模型提出的疑似漏洞称为“候选”。D2是把候选与源码、执行路径和工具证据对应起来的二次核验；支持（SUPPORTED）表示证据支持该候选，反驳（REFUTED）表示证据否定该候选，未知（UNKNOWN）表示证据不足。模型结果有效只表示结果通过格式与候选校验，不表示漏洞已被证明。

token是模型计量文本用量的单位，usage是供应商返回的用量记录。下文的摘要用于确认文件字节身份；“共同有效目标”指三种策略均得到有效模型结果的同一组合约。

发现与核验共享编译记录的修复已进入本批正式运行。新增源码索引和检查模板用于人查看、回查，尚未放入模型提示；模型仍读完整源码（FULL）和原配对，所以本批不能评价模板提示的增益。独立候选审核、精确token公平、真实修复识别和旧133条候选中未知不超过13条的目标仍未完成，研究效果尚未验证。

## 冒烟失败与配置修订

第一个既定SimpleDAO冒烟返回MODEL_CALL_ERROR、requestAttempts=1、usage=null；原网关没有保存底层异常，不能断定其为鉴权、额度或网络故障。原失败和原配置SHA保留，未自动重试。

失败后本地providers配置发生变更，续采预检在runtime.run之前以配置SHA变化阻断，新增模型请求0。端点与模型核对仍相同，单独保存configuration-revision.json的新旧摘要，显式选择当前本地配置；只续采尚未请求的第二个冒烟及159正式单元。不把不同配置阶段伪称为配置全程不变。

第二个既定最长源码冒烟使用相同生产class、网关和提示参数的临时诊断包装；56份生产class与JAR逐字节相同。结果COMPLETED，诊断包装没有额外模型调用、没有改生产源码或JAR。正式159使用原JAR入口。旧133／历史151原件SHA前后一致；第一次失败冒烟不混入正式模型失败分母。

运行中还有一次只修改AGENTS.md可读性规则的提交。HEAD保护在29个正式请求后拦住130个未请求单元，阻断原件中的requestAttempts=null保持原样；通过执行前断言与开始日志独立证明这些单元没有发请求。核对全部生产源码和JAR相同后，只续采剩余单元，分别保存1个部分目标单元和43目标×三策略的129单元。后续每单元仍核对生产源码、JAR和配置，文档提交记录单列。

随后，共享工作区的文档验证执行了Maven重新构建。累计98个正式请求后，JAR摘要保护又拦住61个未请求单元。生产Python／Java源码与有效配置仍相同，新构建111项Java测试及CLI帮助通过；保存新旧JAR摘要及新包56份生产class、60份依赖摘要后，选择新构建继续这61个单元。旧JAR已无可回读副本，包内逐字节相等尚无法复核，因此不声称JAR全程相同。这61条阻断原件的requestAttempts=null保持原样，并通过开始／完成日志及执行前保护位置核对零请求。

第二次续采实际完成49个请求后，共享工作区又一次完成Maven构建，剩余12个无漏洞对照单元被JAR保护拦住。第三份JAR仍由相同生产源码构建，60份依赖摘要相同，但RetrievalSupport.class与ToolCli.class这2份生产class摘要不同，差异原因尚未核实；最新构建111项Java与CLI检查通过。最后12个单元使用第三份JAR的只读同字节临时副本，所有Java调用仅重定向包路径，提示、参数和入口不变。逐请求核对冻结副本与配置，结束后删除临时包与凭证副本。整个正式范围跨98／49／12三个构建产物阶段，不能当作单一二进制产物研究对照。
