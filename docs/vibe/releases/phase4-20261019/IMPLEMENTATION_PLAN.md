# phase 4：访问控制事实引导与双向证据核验

本阶段拟解决两个实际问题：模型指出的敏感操作有时无法进入核验器；一些涉及权限状态和其他入口的候选仍缺少足够证据。计划先统一操作定位，再补权限依赖事实、保护证明和有限执行依据，最后用固定候选与独立标签检验效果。

这里的“双向”指：有证据时支持漏洞猜想，保护证明完整时反驳该猜想，证据不足时保持未知。它不表示每个候选都必须得到确定答案，也不表示已经获得整份合约的安全证明。文献与代码依据见 [ACTaint 分析](ACTAINT_ANALYSIS.md)。

## 2. 首期目标与验收范围

首期聚焦访问控制，重入只做受影响的回归检查。优先覆盖普通以太币转账、已有地址权限写入、简单角色映射及受控状态开关。复杂签名协议、任意代理委托、通用跨合约证明、任意汇编和多交易符号执行不进入首期承诺，识别到后保留缺口。

验收采用四个可观察目标：

- **定位可靠：** 同一编译输入中，发现目录与核验器对同一操作使用相同事实身份；错误或多义绑定仍被拒绝。
- **提示有据：** 模型可以看到关键状态、检查及写入入口的事实，全部能回查当前源码；知识案例与目标事实不混淆。
- **判断有界：** 新增保护规则必须有有效／无效保护对照；执行没有找到见证时保持未知，不改写成反驳。
- **效果可比较：** 固定分母、来源、模型预算和标签；分别统计定位、发现、候选核验与成本，不以反驳数量代替正确性。

例如：一个提现函数检查 `enabled`，另一个入口可以修改它。系统应先定位转账和两个入口，再核对谁能设置 `enabled`、设置后谁能提款、收款人是否受约束。若设置开关本身没有保护，不能因为提现前存在 `require(enabled)` 就反驳漏洞。若业务允许所有人在开关启用后提取自己的余额，也不能把公开调用本身认定为越权。

## 3. 目标方案与取舍

### 3.1 继续复用现有流水线

```text
绑定源码与编译收据
  → 同一操作目录 + 权限状态读写索引
  → 全文 + 有来源的事实提示 + 可选 D1 历史知识
  → 模型提出可定位的候选
  → D2 分别核对保护覆盖与有限执行证据
  → 支持／反驳／未知，附作用范围、原件与缺口
```

新增部分先作为附加记录接入，不建立第二套 Agent 平台或实验运行器。`TECH_DESIGN.md` 继续描述已实现代码，不能提前写入本方案。实施后按证据同步实际成立的部分。

### 3.2 结构种类、语义标签与证明能力分层

`CALL/WRITE` 表示可绑定的程序操作，保留现有含义。拟在目录中增加版本化语义标签，例如以太币转账、委托执行、终止操作、权限状态写入；一个操作可以有多个标签。铸造／销毁等只在实现和资源可确认时标注，不根据 `_mint`、`owner` 等名字直接下结论。

`tx.origin` 与汇编属于需要观察的身份来源或代码区域，先进入事实提示和能力缺口；不能为了凑成六类可执行候选而伪装成 `CALL/WRITE`。是否需要新的候选类型，留到明确的消费需求出现后决定。

每条目录记录拟分别表达：位置能否唯一绑定、机制是否已识别、保护是否可证明、是否存在可执行检查。**能定位而不会证明**是正常结果，应进入未知及具体缺口；损坏身份、错源码、多义操作仍属于失败。

### 3.3 先加事实提示，后评估裁剪和多 Agent

首期使用全文加精简事实。沿用现有单次候选生成，将“敏感操作为何需检查”和“哪些保护可能相关”组织为可定位说明；不新增默认模型调用。模型给出的保护解释是待核对线索，不成为 D2 证据。

之后若有实际缺口，再单独比较代码裁剪或两个专职模型角色。它们必须独立开关、单独计费和计分，不能与目录、图、证明规则同时变更后把所有收益归给某一个组件。

## 5. 每个切片如何实施

### P4-00：先固定候选，区分失败原因

使用 `storage.read_artifact()` 读取 phase 3 原批次，恢复原候选、原源码、目录、编译与工具收据。七项失败须列出候选行号、事实 ID、目录中的操作种类、核验图节点及拒绝条件。首先判断是身份漂移、操作缺失、图表达不一致还是多义匹配；不能根据报告描述直接修改分数。

对 12 条未知分别登记绑定问题、未支持语义、入口／状态缺口、执行／环境缺口等原因，允许一条候选有多个缺口。独立标注“候选确有漏洞／候选错误／证据不足”，审核者和争议另记；程序诊断不能冒充独立真值。

**输出与接缝：** 在原批次之外保存紧凑派生摘要和原件指针，复用 [benchmark_runtime.py](../../../../tools/experiment/benchmark_runtime.py)、[d2_verify.py](../../../../tools/experiment/d2_verify.py)。同时冻结源代码、候选顺序、工具身份与本轮基点。

**通过条件：** 40 个请求、22 条候选、7 项管线失败能复算；错误原因可定位到具体候选；旧 163 条的历史重放与新采集 163 条分组保存。缺失原件时写明不可复核范围，不从摘要重造原候选。

### P4-01：先修复绑定，再扩充可解释的分类

修改范围为 [compiler_facts.py](../../../../tools/experiment/compiler_facts.py)、[risk_catalog.py](../../../../tools/experiment/risk_catalog.py)、[risk_binding.py](../../../../tools/experiment/risk_binding.py)、访问控制调用图，以及必要的 Java 校验与对应测试。优先复用现有低级调用识别，避免再写一套按字符串名称匹配的分类器。

普通 `transfer/send/call{value:...}` 在发现与核验阶段须绑定同一 AST 操作，即使其证明能力尚不充分。终止内置、静态调用、委托调用、内部同名函数必须区分。保留 `sourceHash`、完整源码闭包、编译收据、合约与入口签名、`factId`、原字节跨度及调用上下文；共享内部函数从不同入口到达时，不能只靠一个节点 ID 合并上下文。

标签只能补充业务含义，不替代上述身份。现有模型 schema 2 与历史保存候选先保持兼容；若目录 schema 增加字段，需要 Java／Python 同步验证新旧版本。直接由模型返回操作 ID 等公开协议变化暂不作为首期必需项，实施前在本计划登记具体契约与兼容决定。

**测试接缝：** 同行两个调用、中文／多行字节跨度、重载、继承、内部包装、fallback 入口、真实 builtin 与同名普通函数、错文件／错收据／伪造事实 ID。只允许已唯一证明的绑定，不能通过扩大行号容差达成目标。

**通过条件：** 冻结的七条原始转账候选都进入可解释的绑定结果，预期可唯一定位的项不再因图不认识该操作而失败；超出证明范围的项仍未知。绑定通过不等于七条全部得到漏洞结论；任何无法满足预期的项须列原因，不能宣布该项已修复。

### P4-02：把权限检查与状态修改入口联系起来

在 [focus_context.py](../../../../tools/experiment/focus_context.py) 及编译事实入口上扩展，不将 [program_facts.py](../../../../tools/experiment/program_facts.py) 的词法结果升级为证明。首期种子包括条件读取的状态变量、地址状态、修饰器条件，以及 `msg.sender/tx.origin` 等身份来源。

拟记录四类关系：函数写状态、检查读状态、入口调用函数、检查与操作的控制关系。每条关系保留声明身份、源码跨度、事实 ID、编译收据和关系类型。结构观察与已经证明的支配关系要分别标记；没有入边只说明当前索引没有记录对应检查，不能标成“无权限保护”。

从候选操作向相关检查、权限状态写入者和运行入口展开，保留资源键、别名、状态版本及未知边。真正构造函数与运行入口分别展示，初始化前提仍纳入证据。遇到递归、动态实现、汇编写入或预算耗尽，明确索引不完整，不能静默剪去。

**测试接缝：** 间接受控开关、权限变量的未保护 setter、角色映射键、被错当构造函数的普通函数、检查后改写权限、内部调用与 fallback 绕过。与当前 `relatedEntries` 输出核对，避免遗漏已有索引能力。

**通过条件：** 小型夹具可手工复算节点和边；所有来源可回读；缺边／未知边保留为缺口。默认全文仍原样消费，图本身不改变 D2 裁决。

### P4-03：让模型真正消费经过核对的事实

沿用 [HypothesisService.java](../../../../audit-mvp/src/main/java/com/xhl/audit/HypothesisService.java)、Python 请求组装与现有消费回执。增加显式“事实提示”开关；首期呈现操作、关联检查、相关状态写入入口、构造身份和缺口，不发送目标真值、目标修复版本或目标配对身份。

事实摘要固定排序与预算，记录实际消费项、被省略项、完整消息摘要和模型配置。预算不足必须显式拒绝或按预登记规则省略，并标为不完整；不能裁掉关键检查后称上下文完整。D1 机制卡片仍属于历史知识，它提供待问的问题，当前事实回答位置与关系，D2 才提供裁决依据。

**通过条件：** 假模型接收的实际文本与回执逐字一致；关闭开关时原请求行为可恢复；同一输入和配置可重建相同提示。增加提示会增加成本，需报告完整输入／输出 token 和时间，不承诺文本缩短或效果提升。当前供应商精确 token 预算缺口继续保留。

### P4-04：逐项证明保护，而非扩大“安全”规则

复用 [candidate_proofs.py](../../../../tools/experiment/candidate_proofs.py)、[compiled_d2.py](../../../../tools/experiment/compiled_d2.py) 的六项义务。先将已支持的地址权限检查可靠连接到已绑定普通转账，再考虑直接布尔角色映射，最后考虑有完整写入者集合的简单状态开关。

| 新规则顺序 | 必须同时核对的内容 | 无法满足时 |
|---|---|---|
| 地址权限保护普通调用 | 实际调用者、正确权限槽、全部相关入口、风险前检查与权限版本；外部效果范围明确 | 保留局部检查结果，最终未知 |
| 直接角色映射 | 实际调用者与资源键一致；授予、撤销、初始化及管理角色入口都受有效约束 | 不能由 `roles[msg.sender]` 的表面形状直接反驳 |
| 简单受控状态开关 | 状态初值、允许转换、全部写入者、操作顺序，以及业务是否允许该状态下公开执行 | 状态条件只作前置事实；业务授权或闭包缺失则未知 |

反驳只针对绑定候选、明确授权前提和完整证明范围。状态是布尔值也不代表保护充分；只有时间锁不代表约束了调用者。复杂哈希条件、签名恢复、跨合约角色和任意状态机首期先展示观察与缺口，不假定模型能替代证明器。

**测试接缝：** 正确主体与错误主体、正确键与错误键、检查两侧分支、检查后权限改变、未保护初始化、旁路入口、合法公开兑换、未知外部实现。每个有效保护都有近似但无效的对照；未支持语义不能因名称相似进入完整证明。

**通过条件：** 有效保护在明确范围内取得全部必要义务；同组漏洞及错误保护不被反驳；缺收据、超时和截断依然未知或失败。每条新反驳都记录新增证据及证明范围，不以新增反驳数量验收。

### P4-05：复用执行见证，补齐真实正反对照

先使用 [evm_witness.py](../../../../tools/experiment/evm_witness.py) 已有的标量权限写入及敏感消费者回放，建立正确保护、错误保护、未初始化、正常提交和回滚的对照。CEI 表示检查、状态更新、外部交互的顺序；其执行顺序反例继续只按原有限属性解释，不等同于完整重入获利证明。

每份见证绑定原字节码、初始化、调用者、权限或资产资源、风险源映射、正常提交效果，以及两个独立节点的重放。不得直接改写存储来制造攻击初态；没有正常提交、没有敏感消费者、没有授权规则依据，都不能只凭一次调用成功支持业务越权。

**执行失败的处理：** 没有找到见证、交易回滚、预算耗尽和环境不支持分别记录，均不推导安全。要反驳候选，应由 P4-04 的完整保护证明给出；有限搜索未命中不充当全称证明。

真实维护者修复继续引用 [phase 2 的 SYN-02](../R2-20261010/IMPLEMENTATION_PLAN.md#synapse-优化任务)与[真实案例先导](../R2-20261010/attachments/REAL_CASE_PILOT.md)。先检查能否用同一范围解释漏洞侧与修复侧；无法覆盖时报告缺口，不用人工补丁冒充维护者修复，也不重命名已用于开发的样本为独立测试。

**通过条件：** 已支持的执行断言和原始收据可复核；新规则在固定候选上的每次状态变化有独立程序依据。至少一组访问控制真实修复完成双方证据，才可声称取得真实双向对照；没有取得时只完成设施验收。phase 2 的重入修复要求不被本计划取消。
