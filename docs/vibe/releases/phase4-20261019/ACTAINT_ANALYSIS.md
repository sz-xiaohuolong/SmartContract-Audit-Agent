# phase 4：访问控制事实引导与双向证据核验——ACTaint 文献与工程分析

ACTaint 对本项目最有价值的启发，是先把“哪些操作值得检查、哪些函数会改变权限”整理成可定位的程序事实，再让模型判断业务含义。VeriRAG 已有编译事实、候选核验和有限执行能力，下一步应补齐这些能力之间的衔接，并扩大有明确边界的保护证明。本次分析支持这一优化方向，但不能证明本项目已经优于 ACTaint。

2026-10-19 完成原文、相关源码、历史批次原件及局部测试核对。本文是规划依据，实施顺序与验收集中在[统一优化计划](IMPLEMENTATION_PLAN.md)。本阶段就是此前口头所称的 R4；文档显示名称改用 **phase 4：访问控制事实引导与双向证据核验**。

## 2. ACTaint 实际解决了什么问题

访问控制判断需要同时回答两个问题：操作是否需要特定权限，以及调用者能否在没有该权限时实际完成操作。例如，公开出售管理权可能是合约约定的业务；一个名字像构造函数、实际却能被任何人调用的初始化函数，则可能意外改写权限。仅看到 `owner`、`transfer` 或公开入口，都不足以判定越权。

论文让两个模型角色分别负责识别敏感操作和追踪输入影响。静态分析提供定位依据，模型解释业务语义并复核自己的路径推断。这里的“污点”指来自外部、可能受不可信调用者控制的信息；“汇点”指需要检查的敏感操作；“净化器”指能够限制相关输入或执行条件的检查。

### 2.1 关键变量依赖图并不是完整路径证明

原文 §III-B、图 4（第 3—4 页）将**用于条件检查的状态变量，以及地址类型的状态变量**列为关键变量，还分析修饰器中的状态引用。范围并不限于直接与 `msg.sender` 比较的变量，因此可以包含余额、授权额度、状态字符串等。

关键变量依赖图（CVDG）主要记录函数与变量之间的关系：函数写变量时建立“函数 → 变量”边，函数在条件中读取变量时建立“变量 → 函数”边。它能提示“谁能修改这个检查所依赖的状态”，但不能单独证明某条交易路径可行，也不是 Gemini 描述的通用变量到变量的精确数据／控制依赖图。

论文在运行图中排除真正的构造函数，并用静态识别结果提醒模型不要混淆构造函数与普通函数。VeriRAG 可以借鉴这一分类，但不能丢弃构造和初始化证据：当前权限来自谁、是否可重复初始化，仍是后续证明的前提。

### 2.2 原文的六类操作

原文 §III-C.1（第 4—5 页）的分类如下。它是论文的候选识别策略，不是适用于所有工具的漏洞标准，也不意味着每种操作都存在访问控制问题。

| 原文类别 | 对本项目的含义 |
|---|---|
| 修改关键变量 | 检查状态写入与权限使用的关系；角色修改、余额变化可作为下位业务语义 |
| 合约终止操作 | 定位 `selfdestruct` 等实际内置调用；后果需结合固定 EVM 环境判断 |
| 低级调用 | 区分 `call`、`staticcall`、`delegatecall`，不把调用种类当作越权结论 |
| `tx.origin` 使用 | 记录身份检查来源，区分交易发起者与直接调用者；不是普通转账汇点 |
| 以太币转账 | 定位 `transfer`、`send`、带 value 的调用；代币转账需要另行确认实现和资源 |
| 内联汇编 | 记录高层分析可能遗漏的效果与能力缺口，不能把未知汇编当作无影响 |

Gemini 将后三类中的部分内容改成“铸造／销毁、特权变更、关键状态写入”，遗漏了 `tx.origin` 和汇编。铸造、角色管理值得在本项目中细分，但必须标为**工程扩展**。原文还明确不讨论 `callcode`，不能把它写成原文的既定覆盖范围。

### 2.3 全文、静态提示与两个模型角色

原文 §III-C.2（第 5 页）明确指出只靠代码切片不够，采用整个合约配合静态提示。Sink Agent 根据候选操作和函数／状态关系，判断哪些位置值得进行权限分析；Taint Agent 再检查来源、传播路径及限制条件。两个角色分别有自评步骤（§III-C.5、III-D.3），并非最后增加一个独立、确定性的验证器。

因此，直接把全文缩短一半并不能算复现 ACTaint。对本项目更稳妥的首期做法，是保留全文，增加精简、可回查的权限事实提示，再单独测量这种提示是否改善定位与判断。

### 2.4 模型路径解释的证据边界

论文明确说明模型不能实际执行合约，而是推断路径。它没有给出普适的形式化可靠性证明。Gemini 给出的数学判据是二次整理，不是论文定理；路径中“没有任何检查”也不是必要条件，因为存在检查但检查错主体、错资源或被后续状态变化破坏，同样可能越权。

对 VeriRAG，应把以下内容分开保存：程序可观察事实、业务授权规则、模型猜想、路径可行性证据、保护覆盖范围。发现一条可执行路径只能说明行为能发生；还需要确认其违反了明确的授权规则。反过来，一次运行没有触发问题，也不能证明所有允许状态和入口都受保护。

## 3. 实验数字说明了什么

TP 表示正确报告的漏洞，FP 表示错误告警，FN 表示漏掉的漏洞。精确率是 TP／(TP+FP)，召回率是 TP／(TP+FN)，F1 是二者的调和平均。论文采用函数定位并按根因／执行路径去重，不能与本项目的目标级分类或候选核验数量直接比较。

### 3.1 主要效果与不可忽略的数据限制

| 数据与方法 | TP／FP／FN | 精确率 | 召回率 | F1 |
|---|---:|---:|---:|---:|
| 15 个 CVE，ACTaint | 14／1／1 | 0.933 | 0.933 | 0.933 |
| SmartBugs 624 个合约，ACTaint | 425／258／56 | 0.622 | 0.884 | 0.730 |
| 同组，AChecker | 369／315／112 | 0.539 | 0.767 | 0.633 |
| 同组，GPTLens | 155／242／326 | 0.390 | 0.322 | 0.353 |
| ACFix 派生集，ACTaint | 36／17／63 | 0.679 | 0.364 | 0.474 |

数据来自表 I—III（第 7—8 页）。Gemini 对 AChecker 的精确率 0.528、召回率 0.791 与本机原文表 II 不符，应使用上表数值。

还有四个限制直接影响我们的实验设计：

1. **624 份合约来自 AChecker 已报告的集合。** 不是从 47,398 份 SmartBugs Wild 合约随机抽样，不能推断全库覆盖或所有现代合约上的效果。作者通过两名研究者独立标注和第三人裁决得到 481 项漏洞，并将 41 个符合业务意图的案例视为安全。
2. **ACFix 的最终集合是 93 份、99 项漏洞。** 原始 113 份扣除 19 份重叠和 1 份作者认为无实际漏洞的样本；46 份可编译，47 份采用去静态分析版本。引言写 94，实验部分写 93，应说明这处不一致，并以 §IV-B.3 的最终处理为准。论文还说明 AChecker 在该集上的结果受编译限制，不具有完整可比性。
3. **15 个 CVE 不是充分的负例评价集。** 它适合检查已知漏洞定位，却不足以衡量修复后误报；“召回提高 40%”也不是论文提出的复现门槛。
4. **存在人工预处理与标签判断限制。** 作者调整了部分旧语法合约，并对潜在但未计入正式标签的发现另作讨论。我们需要保存原始输入与派生输入，预先说明计分范围。

### 3.2 消融支持静态引导，但未隔离每一项贡献

表 IV（第 9 页）中，完整方法的精确率／召回率／F1 为 0.622／0.884／0.730；去掉静态分析后为 0.538／0.281／0.369；去掉 Taint Agent 后为 0.281／0.940／0.432。

这说明在该实验设置中，静态信息对发现很重要，后续污点分析能过滤大量候选。但 NoStatic 同时移除了关键变量、图和操作提示，不能把全部差异归因于 CVDG 一项，更不能解释成“已证明注意力分散是唯一原因”。NoTaint 把敏感汇点直接作为结果，也不等价于隔离了多 Agent 数量本身的收益；论文没有单独给出自评开关的消融。

表 V 的 DeepSeek-R1 为 0.652／0.902／0.757，GPT-4o-mini 为 0.145／0.938／0.251。这是当时模型、提示与数据的结果，足以提醒我们核验底座影响，不支持替所有小模型下永久结论，也不能移植为当前项目模型的预期成绩。

### 3.3 258 个 FP 不能全部归因于虚构路径

258／(425+258) 约为 **37.8%**，表示报告出的告警中错误告警的比例。通常的误报率是 FP／(FP+TN)，其中 TN 表示正确排除的负例；缺少对应负例分母时不能计算这个指标。

原文 §VI-A（第 9 页）讨论了业务意图误解和复杂隐式权限：包括正常代币管理、付款换取权限、签名校验及游戏规则。这些行为有的确实能够执行，只是并不违反业务规则。因此，执行回放可以排除某些路径猜测，却不能自动解决全部误报，更不能据此承诺精确率达到 95%。

论文结尾已提出结合符号执行、抽象解释等后续方向。我们的研究主张应聚焦可复核的实现与实验结果，不能只因加入执行工具就宣称首创或超越。

D2 的六项义务分别核对主体、资源、风险前检查、入口覆盖、状态版本和绕过路径。这里还有一个易误读点：**保护义务被反驳**可能支持漏洞候选；**漏洞候选被反驳**则要求保护证据完整。两层对象相反，不能仅统计 JSON 中出现的 `REFUTED` 字样。

### 4.1 最近的七项失败究竟是什么

本次重新读取批次 `be23621ebe4f404e956a5f4261d5810d` 的 40 条结果，原始字节 SHA-256 为 `b61ee5ae31ffab8e767ab675fc853bcc2c9fe78d73a85875bfe19ced3abde1f1`。核对得到 33 项管线完成、7 项失败；22 条候选为 10 支持、0 反驳、12 未知，与原报告一致。

七项失败集中在 `Missing.withdraw` 的 `owner.transfer(this.balance)` 两次，以及 `Phishable.withdrawAll` 的 `_recipient.transfer(this.balance)` 五次。源码中发现目录使用的图与访问控制 CALL 证明图不同，后者只专门实现终止内置调用；`risk_binding` 又要求可接受的调用种类。因此目前证据指向**发现与核验对普通转账调用的表达不一致**，不是“只要扩充标签便能解决”。具体 AST 和图节点需在实施首项用原候选重现后逐项确认。

修复绑定只能让候选进入正确的核验分支。`owner.transfer` 是否违反业务授权、`tx.origin` 检查是否存在可行绕过，仍须分别取证。七项不能预先全部指定为漏洞支持或反驳。

### 4.2 为什么“0 条反驳”不能单独当成根因

上一轮安全对照没有生成漏洞候选，本来就不会提供可供 D2 反驳的负例。其余未知还包括绑定失败、证明能力不足和路径／环境缺口。必须先对候选独立标注和分组，才能判断应该增加哪种证明。

旧 163 条固定候选的 82／0／81、2026-10-14 新采集 163 条的 83／0／80，以及本次 22 条的 10／0／12，属于不同来源或运行，应分别保存。不能将 81 个未知全部解释成“已有隐式保护的误报”，也不能把“反驳数增加”单独作为优化成功标准。

## 5. 对 Gemini 建议的取舍

| 建议 | 本次判断与处理 |
|---|---|
| 用静态结构引导模型关注权限 | 采纳；增加可定位的状态读写和检查关系，沿用全文输入 |
| 采用六类敏感操作 | 采纳分类思想，纠正原文类别；结构类型与业务语义分层，允许多标签及未判定 |
| 将 Prompt 压缩 50% 以上 | 没有原文或本项目证据支持；列为后续单独研究，不作首期验收 |
| 通过扩充枚举使绑定率 100% | 不采纳这种保证；仅要求冻结的可支持回归集合正确绑定，同时验证错误绑定拒绝 |
| 用 Sanitizer 识别把大量 UNKNOWN 改为 REFUTED | 仅采纳“扩大保护条件观察范围”；只有完整证明满足时才反驳，观察到检查不等于防御有效 |
| 生成单测，运行失败就反驳漏洞 | 不采纳。未触发、回滚、超时和环境缺失均不能排除其他输入或状态 |
| 引入两个或更多模型角色 | 保留为可选消融；先改善单次请求与确定性核验，不先增加成本和编排复杂度 |
| 宣称已经超越 ACTaint | 不采纳。当前可谈证据绑定与有限回放的实现差异；准确性优势待同口径独立实验 |

Gemini 的 `AntiACTaintVault` 也不能直接作为强反例：片段中 `emergencyBlock` 默认是 0，且没有赋值入口，所以条件在给出的代码中始终不成立；`designatedSigner` 从未参与校验，“特定签名激活”没有代码依据。若补上允许进入特定区块的设置函数，时间条件又不必然约束收款人和调用者。可将它改造成三组机制夹具：永不启用、受授权启用且固定受益人、任何人可启用并控制受益人；分别标明业务规则和可达状态，但不能预言 ACTaint 一定误报。

## 6. 对工程和论文的真正启发

第一，**把敏感操作定位与漏洞判断分开**。统一发现目录、候选身份和核验图，首先减少“模型说的是这个操作，证明器看到的却是另一个操作”的失败。

第二，**把权限状态的来源补进检索与提示**。借鉴 CVDG，将检查、受其影响的操作和可能修改该状态的其他入口连起来。D1 历史知识可以提示检查方向，当前合约的事实必须重新绑定，不能继承历史案例的授权结论。

第三，**用业务负例与完整保护证明检验误报**。合法公开操作、受控状态开关、正确角色映射和近似错误保护，都比单纯增加漏洞样本更能检验方法。保护证明、执行见证和模型解释分别报告，允许最后保持未知。

可以检验的研究问题是：“在固定候选和独立标签下，加入权限事实引导及有范围说明的程序证据，能否减少错误支持和错误反驳，并提高可裁决覆盖？”它比承诺某个精确率或把所有未知清零更符合现有工程，也便于解释无增益的结果。
