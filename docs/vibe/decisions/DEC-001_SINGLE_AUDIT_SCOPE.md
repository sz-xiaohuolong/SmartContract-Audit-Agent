建议先把现有本机实验台改造成可逐步回看的审计工作台：从已激活的正式 Milvus 快照召回知识，运行 D1 选择器，生成结构化漏洞假设，收集静态分析证据，再由初版 D2 检查保护条件，逐样本保存运行报告。先以离线夹具验收整个链路，再由使用者逐次显式选择真实模型运行。工程链路完成不代表 D1 或 D2 的科研效果已成立。

## 可选方案

| 方案 | 做法 | 优点 | 代价和风险 |
|---|---|---|---|
| A：复用本机 Python 编排和 Java CLI（推荐） | 在 `tools/experiment/` 新增运行编排；本机 HTTP 页面调用它；正式快照只读，复用 Java 检索与模型／工具能力 | 改动集中、离线测试容易、保留现有技术栈与报告目录 | Python 与 Java 间仍通过子进程和版本化 JSON 通信，需要严密校验超时与产物 |
| B：把整条链路迁入 Spring Boot REST | 在 `audit-mvp` 内新增持久任务和 HTTP API，并迁入快照、向量查询与运行管理 | 后续部署更统一 | 需要重新实现已验证的 Python 谱系和快照逻辑，迁移范围大，短期增加不一致风险 |
| C：立刻引入多智能体工作流与深度符号执行 | 将 D1、模型、工具、D2 分成多个智能体和多轮调用 | 可尝试更复杂方法 | 请求量、状态空间和错误归因急剧增加；当前真实标签不足，难以验证收益 |

建议选择 A，并把 API 与报告契约版本化，以便后续确有需要时迁入 Spring Boot；不引入新付费供应商或真实运行的自动重试。

## 建议的产品边界

1. 页面提供**已登记的本机开发样本**选择、正式知识快照状态、D1 候选和条件绑定预览、运行按钮、阶段状态与逐样本结果回看。知识、锁定测试和未通过来源核验的样本不得作为默认检测目标；未审开发样本只能用于工程联调，报告标 `researchEligible=false`。首版不接受浏览器上传任意合约，也不开放公网或多用户权限。
2. 默认“离线演练”使用固定夹具和假模型／假工具，零真实 API 请求；“真实运行”须在页面上单独显式选择并展示本次最大请求数、输出 token 上限、无自动重试及所选端点。页面加载、状态查询、历史回放和报告下载都不能触发付费调用。
3. 一次真实工程运行限定为 `1 样本 × 1 D1 策略 × 1 重复 × 1 模型阶段 × 0 重试`，最多一次模型请求。若 D2 初版无法仅用已有源码和工具证据作出判断，就记录 `UNKNOWN`，不额外调用模型。更大的批量与公平对照另行冻结 token 模板、样本和预算后实施。
4. 现有 `mvp_` 工程记录只读保留；正式 `s1b_` 集合只读访问。遇到快照不一致、跨组泄漏、embedding 不匹配、工具不可用或产物损坏时停止该样本并报告具体阶段。不得静默回退到 `mvp_` 集合。

## 建议的技术链路与数据契约

`已登记目标源码 → 谱系及 SHA-256 校验 → 同一固定 BGE 模型编码 → 正式 Milvus 召回 → Java D1 条件绑定／互补选择 → 一次结构化模型假设 → Slither／可选 Mythril 工具证据 → D2 保护义务检查 → 原子持久化 → 页面回看`。

- 检索输入沿用 `recall.py` 的快照、catalog、源码摘要和共享候选池契约；仅在正式快照的 `active.json`、Milvus 全量读回和目标谱系都一致时运行。原 `recall_pool` 目前要求目标位于快照审核清单，实施时需增加受限的**外部开发目标**谱系校验接口，不改写正式快照；具体准入规则写入新 SPEC 后测试。
- 模型阶段沿用 `audit-mvp` 的严格 JSON Schema 和逐字段校验；当前三字段只能表达初步结论，不能表达精确位置与保护义务。新版本须定义可校验的假设字段（类别、位置、风险操作、理由、证据引用），并将旧版结果视为历史记录，不进行破坏性回填。模型输出不是 D2 真值。
- 工具结果需保留引擎、命令版本、状态、可审查位置／消息及耗时；空告警不等于安全证明。D2 初版只消费固定的保护义务（主体、资源、调用顺序、入口覆盖、状态版本、旁路）及已有事实／工具证据，输出 `SUPPORTED / REFUTED / UNKNOWN` 和引用。任何一个关键义务缺证据时，最终判断仍为未决。
- 新报告独立写入 `.local/audit-runs/<runId>/`：`plan.json`（源码、谱系、快照、模型和预算摘要）、`events.jsonl`（阶段事件）、`sample.jsonl`（逐样本完成记录）、`result.json`（页面读取的版本化汇总）。每条完成记录落盘并同步；中断后只读恢复，不自动重复付费请求。失败、超时、解析错误分别计入分母；usage 缺失为 `null`。密钥、完整原始模型响应和不必要的源码全文不进入页面 API。
- 页面新增本机受限 API：列出准入目标、预览正式快照与检索证据、显式创建运行、查询运行与下载报告。接口仅监听 `127.0.0.1`，校验 Host／Origin、请求大小、样本 ID 白名单和运行并发；不接受客户端传入文件路径、模型端点或系统命令。

## 2026-10-05 计划前发现的目标事实缺口（已决定）

对已登记开发源码运行现有 `program_facts.py` 后，`AC-ASE-006` 只提取到两条 `CHECK`，`AC-ASE-009` 只提取到一条 `WRITE`；正式访问控制知识对的风险操作为 `CALL`。现有 D1 契约要求目标风险操作与案例一致，因此这两份短源码无法提供该知识对的有效条件绑定。`RE-SCRUBD-001` 的完整源码约 148 KB，虽能提取 `matchOrderWithReserve` 中第 608 行的 `CALL`，其函数范围约 5.9 KB，完整合约仍超出单次模型提示硬上限；该函数还包含分支和复杂调用，绑定预计为 `UNKNOWN`。这些是工具实测事实，不能靠强行更改知识案例类型或伪造程序事实消除。

| 选择 | 行为 | 影响 |
|---|---|---|
| A1：增加明确的函数级工程试跑（推荐） | 对固定开发样本 `RE-SCRUBD-001` 允许选择经源码摘要核验的 `matchOrderWithReserve` 函数；事实提取和工具仍看完整源码，模型只看带原始行号的函数片段，报告标明“函数级、上下文不完整、非科研结果” | 能在真实重入源码上演练正式知识快照与 D1 的 `UNKNOWN` 边界；不能称为完整合约检测，需增加函数片段边界与提示校验测试 |
| A2：保持原规格的整份源码上限 | 两份短访问控制源码可以进行模型试跑，但 D1 无匹配风险操作；两份重入源码保持阻塞，完整 D1 链路仅在离线夹具运行 | 最少改动，但真实案例无法演练正式 D1 的端到端接线；页面必须清楚展示该限制 |

建议 A1，不提高一次真实运行的模型请求上限、不改变数据划分、正式知识快照或研究标签。若获批准，需修订 `SPEC.md` 和 `PROPOSED_DESIGN.md` 的输入边界，然后再写实施计划；若选择 A2，则按现有规格实施，并明确该限制仍未解决。
